# TipHUD — статический аудит подавления изображения

**Гейт BLOCKED.** Для Steam 1.09/build 12996889 и UE4SS `83330635`
отдельная настройка цвета корневого TipHUD доступна в отражении. Статика
не подтверждает, что она подавляет только экранные пиксели и сохраняет
заимствованный World-значок. Основа аудита `35f205adc96137051cd28c51bdaca07861bd8bb3`.

## Владельцы состояния и отрисовки

- `PlayerActionComponent+0x410` даёт выбранного владельца. `IIPInteractionSource`
  проверяет экранный компонент (`bVisible`, `bAddedToScreen`), состояние TipHUD
  и готовность исходного текста. `IIPOpenVisibility` и `IIPHintSource` проверяют
  `Visibility`, `RenderOpacity`, `bIsEnabled` и валидность нужных объектов.
  Корневой `ColorAndOpacity` в эти предикаты не входит. `CanShow` вызывает
  native parent и учитывает режим ввода. Blueprint Tick пишет `RenderOpacity`
  0/1, `SetupTipMessage2` поставляет локализованный текст, а отдельная ветка Tick
  обновляет `t` для прогресса удержания в материале Retainer.
- В TipHUD `CanvasPanel_0 → HorizontalBox_4 → CanvasPanel_6` содержит соседние
  ветки `TextBlock_89`, `RetainerBox_0 → ImageInteractAllowed` и
  `CanvasPanel_2 → ImageInteractNotAllowed`. `IIPHintSource` берёт MID через
  `GetEffectMaterial` и использует его для World-изображения. Замена текстуры,
  alpha материала или параметра `t` затрагивает заимствованный источник.
  [World-код и доказательства](../selected-owner-world/README.md),
  [статическая иерархия](../../../../docs/VERIFIED_RUNTIME.md).
- В UE4.27 `FWorldWidgetScreenLayer::AddComponent` передаёт `TakeWidget()`
  экранному слою Slate. `SWorldWidgetScreenLayer` помещает его в проецируемый
  `SConstraintCanvas`. Общий слой обслуживает и другие компоненты. Материальный
  `TintColorAndOpacity` у `UWidgetComponent` используется в World-маршруте,
  экранный путь не использует этот материал. Общего для текста и обоих значков
  отдельного финального композита на компоненте в проверенной цепочке нет.
  [WidgetComponent](https://github.com/AlexMercer-MA/UnrealEngine-4.27/blob/306a7e9f7fb53f14c2cb3bfd3854ad906710a17e/Engine/Source/Runtime/UMG/Private/Components/WidgetComponent.cpp#L57-L111).

## Точки вмешательства

| Точка | Влияние и решение |
| --- | --- |
| `Visibility` / `RenderOpacity` у корня или проверяемых потомков | Прямо ломает текущий readback. Tick также владеет `RenderOpacity`. Одной обратимой записи недостаточно для сохранения штатной семантики. |
| Screen layer, смена Space, удаление screen widget | Смена членства затрагивает `bAddedToScreen` и native путь. Вмешательство в общий слой затрагивает посторонний HUD. Смещение за экран меняет геометрию и может исключить Retainer из отрисовки. |
| Финальная поверхность `RetainerBox_0` | Только ветка разрешённого значка. Текст и locked-значок выводятся отдельно. Изменение общего MID также затрагивает World. |
| `UUserWidget::SetColorAndOpacity` на точном экземпляре TipHUD, исходный RGB и alpha 0 | Наиболее узкая точка для проверки. Отражённая сигнатура `void SetColorAndOpacity(FLinearColor)` есть в локальном UHT `UMG/Public/UserWidget.h`. UE4.27 сохраняет отдельный `ColorAndOpacity` и обновляет `MyGCWidget`. `SynchronizeProperties` может подключить `ColorAndOpacityDelegate`. В локальном экспорте TipHUD явного свойства/биндинга не найдено, отсутствие живой привязки или конкурирующего writer ещё предстоит подтвердить. Вызов и чтение значения через точный UE4SS для этого экземпляра не проверялись. [UserWidget](https://github.com/AlexMercer-MA/UnrealEngine-4.27/blob/306a7e9f7fb53f14c2cb3bfd3854ad906710a17e/Engine/Source/Runtime/UMG/Private/UserWidget.cpp#L279-L305). |

В проверенном исходнике `SRetainerWidget::OnPaint` создаёт контекст из
`InWidgetStyle` и передаёт его в `PaintRetainedContentImpl`. Этот контекст
идёт в `DrawInvalidationRoot`, а slow path передаёт `Context.WidgetStyle`
в `SCompoundWidget::OnPaint`. Финальная экранная поверхность Retainer
также умножается на tint контекста. Следовательно, корневой tint нельзя
считать изолированным от offscreen-захвата. Ненулевой старый кадр в RT
может временно скрыть проблему до следующего repaint. Из исходников нельзя
вывести, останется ли реальный World-значок свежим и видимым на этой сборке.
[SRetainerWidget](https://github.com/AlexMercer-MA/UnrealEngine-4.27/blob/306a7e9f7fb53f14c2cb3bfd3854ad906710a17e/Engine/Source/Runtime/UMG/Private/Slate/SRetainerWidget.cpp#L475-L666).

## Этап A — надстройка только в исходниках

Контроль — [Selected-owner World](../selected-owner-world/README.md),
source `2e167227e8b29c692fdd9157de06c5cf7ed4660f`, результат `66912dd`.
Существующий игровой прогон проверил путь выбора и World lifecycle на
обычных переходах через NONE. Он не проверял запись tint. Из известных
вариантов A даёт самый короткий путь к различению эффектов для Screen и
World: меняется ровно один корневой параметр, при сохранении прежнего MID
и обычного обновления кнопки.

Для воспроизводимой офлайн-подготовки взять чистую отдельную копию
`selected-owner-world/Scripts` указанного source и сверить 13 Lua по
его `SOURCE_MANIFEST.json`. Из корня этой копии (с подкаталогом `Scripts`,
вне рабочего дерева исходного checkout) применить
`git apply --unidiff-zero <абсолютный путь к stage-a.patch>`, затем положить
[IIPTipHUDTint.lua](IIPTipHUDTint.lua) в её `Scripts`. Нулевой контекст
патча предполагает строго эту исходную идентичность. В результате 14
Lua, из исходных изменены только три. Локальная конфигурация и ресурсы
остаются внешними и проверяются отдельно перед будущей установкой.
Надстройка не является установочным пакетом.

- `Ctrl+Alt+F10` только ставит команду. Native-доступ идёт из существующего
  EngineTick pump. Для записи нужны уже показанная пользователю World-панель,
  программный `World.shown()`, тот же выбранный Open и свежий readback.
  Проверки повторяются в двух соседних проходах; смена RGBA, привязка,
  неожиданный тип или несовпадение owner/component/widget исключают запись.
- Закреплённый UE4SS регистрирует Lua pusher для `FDelegateProperty`. Он
  возвращает объект и имя функции. Probe принимает только пустой объект и
  `NAME_None`; живое чтение ещё подлежит проверке. Это проверка известного
  binding, плюс два readback цвета для обнаружимого writer. Запись того же
  значения или смена с возвратом между выборками остаются неразличимыми.
  [Регистрация pusher](https://github.com/UE4SS-RE/RE-UE4SS/blob/83330635/UE4SS/src/UE4SSProgram.cpp#L1309),
  [чтение значения](https://github.com/UE4SS-RE/RE-UE4SS/blob/83330635/UE4SS/src/LuaType/LuaUObject.cpp#L1956-L1981).
- Окно ограничено первым из двух пределов: 5 секунд по целочисленным
  системным часам или 300 проходов pump. На границе требуется следующий
  доставленный callback. Повторная клавиша завершает окно. Потеря World
  или исходного readback, уход с owner и штатный STOP тоже закрывают его.
  Перед явным hide/release сессия пытается восстановить RGBA. Если сам
  World скрылся внутри refresh, попытка следует в том же callback.
  Исходный цвет возвращается только живому объекту с повторно проверенными
  путём, классом, адресом и связями, пока значение совпадает с нашим RGBA
  и делегат пуст. Совпадение исходного RGBA уже означает возврат значения;
  запись в него не повторяется. После неясной записи или восстановления
  новые окна блокируются до перезапуска кандидата.
- `EndPlay` выбранного актора и `LoadMapPre` аннулируют активное окно без
  native setter. Потеря объекта, прерывание callback, изменение свойства
  другим writer и остановка tick могут оставить восстановление
  неподтверждённым. Точное повторное нахождение и native IsValid сужают риск
  stale UObject, но не предоставляют отдельный serial для самого TipHUD.
  Исторический прогон World потерял финальный cleanup-ack на выходе.
  Поэтому сценарий ограничен стабильной картой и живым Open до
  подтверждённого возврата Screen. Таймаут не является гарантией на
  остановленном процессе.
- В покое новый код не читает TipHUD. В окне он читает одну цепочку и
  native snapshot на существующем шаге. При штатном опыте две записи
  setter на границах. Нет запроса принудительного capture, нового GPU pass
  по инициативе probe или циклического переключения. Смена tint сама
  может вызвать invalidation и repaint; их реальная стоимость открыта.

## Точный будущий прогон A

1. После отдельного разрешения и закрытого хоста сверить идентичность
   кандидата, локальные ресурсы и план отката. Запустить обычное сохранение
   и подойти к одному доступному Open. Дождаться `SHOWN` и увидеть обе
   подсказки. Зафиксировать язык, устройство, текст, разделитель, значок
   и соседние элементы HUD в контрольной записи.
2. Нажать `Ctrl+Alt+F10`. Сопоставить видео с `TINT_APPLIED`. Следить
   отдельно за Screen, World-текстом, разделителем и кнопкой. Если оба
   устройства доступны, переключить ввод обычным движением или нажатием,
   которое не активирует объект, пока окно ещё открыто. Сравнить значок
   с ожидаемым для нового устройства и повторить эту смену в контроле.
   При недоступной смене устройства динамическая часть остаётся открытой.
   Один кадр и совпадение указателя MID ничего не говорят о свежести RT.
3. Немедленно повторно нажать клавишу при пустом, неверном или зависшем
   значке, мерцании, пропаже World, изменении native readback или
   соседнего HUD. Проверить возврат Screen и `TINT_RESTORED` /
   `TINT_ORIGINAL_PRESENT`. `TINT_REFUSED` означает прекращение опыта,
   `TINT_STOPPED` — неопределённый возврат или обнаруженный writer.
   Если возврат не подтверждён, прекратить опыты в этом процессе,
   штатно закрыть игру и выполнить проверенный откат при закрытом хосте.
4. Если ручной возврат прошёл, отдельным коротким окном наблюдать таймаут
   на том же объекте. При стабильном результате можно в следующем окне
   обычным отходом вызвать NONE и проверить, что восстановление в журнале
   предшествует HIDDEN. После возврата к Open увидеть обе подсказки.
   Выход, загрузку карты, гибель и принудительную выгрузку в активном
   окне не использовать как проверки.
5. Сопоставить соседние кадры контрольного и экспериментального окон,
   включая обе границы. Если доступен согласованный capture frame time,
   сравнить последовательности отдельных кадров на том же объекте и
   при том же вводе. Средний FPS не заменяет наблюдение всплеска. При
   отсутствии capture заключение ограничить визуальными наблюдениями.

## Когда переходить к B или C

В UE4.27 запись `UUserWidget` обновляет сохранённый цвет и стиль GC-widget.
Дальше repaint зависит от пути Slate. Retainer в `OnPaint` получает
входной стиль, при подходящей фазе или invalidation может обновить RT
через `DrawInvalidationRoot`, а затем формирует экранный draw element
с тем же tint. Захват может ждать бюджета Retainer и передаваться в
render thread отложенно. `RequestRender` лишь ставит запрос и
инвалидирует порядок детей. Поэтому два setter в одном callback не
дают доказательства промежуточного захвата. Даже успешный захват с
непрозрачным стилем может создать Screen draw element в том же
`OnPaint`. Свежесть RT в момент использования World и видимость
конкретного экранного кадра устанавливаются в игре. [UE4.27 Retainer paint](https://github.com/AlexMercer-MA/UnrealEngine-4.27/blob/306a7e9f7fb53f14c2cb3bfd3854ad906710a17e/Engine/Source/Runtime/UMG/Private/Slate/SRetainerWidget.cpp#L356-L599).

Если A даёт прозрачный или старый значок, сначала сопоставить момент
потери/обновления с изменением ввода и возвратом исходного цвета.
Обычный возврат после окна уже даёт контрольное наблюдение. Для
отдельного B нужны наблюдаемые границы capture и экранной композиции;
циклическая непрозрачность без них рискует показать дубль и вызвать
дополнительные paint/pass. Если capture возможен только в кадре с
видимым оригиналом, приоритет C. Начать с проверки входной кисти
`ImageInteractAllowed` и native параметров текущего значка: если
готовая входная текстура меняется штатно, можно проверить приватный
визуальный ресурс World на тех же данных. Простой alias MID/RT не
разрывает зависимость, если сам захват уже прозрачный. Нужно доказать
отдельно получение свежего ресурса, корректное отображение на обоих
устройствах, переназначение и применимые состояния, включая удержание.
До результата A код B/C не требуется.

## B — граница Retainer и Screen, проверка исходников

`URetainerBox::RequestRender` вызывает одноимённый метод Slate. Тот
ставит `bRenderRequested` и инвалидирует порядок детей. `OnPaint`
строит `FSlateInvalidationContext` из входного стиля, затем синхронно
проходит `PaintRetainedContentImpl` и формирует Screen `MakeBox` из
того же стиля. `DrawInvalidationRoot` подготавливает draw buffer и
передаёт обновление RT через `AddWidgetRendererUpdate`. Порядок вызовов
на game thread здесь не доказывает момент исполнения GPU. Даже если RT
обновится позже, Screen draw element уже собран с tint текущего прохода.
[RetainerBox.cpp](https://github.com/AlexMercer-MA/UnrealEngine-4.27/blob/306a7e9f7fb53f14c2cb3bfd3854ad906710a17e/Engine/Source/Runtime/UMG/Private/Components/RetainerBox.cpp#L43-L49),
[SRetainerWidget.cpp](https://github.com/AlexMercer-MA/UnrealEngine-4.27/blob/306a7e9f7fb53f14c2cb3bfd3854ad906710a17e/Engine/Source/Runtime/UMG/Private/Slate/SRetainerWidget.cpp#L356-L599),
[WidgetRenderer.cpp](https://github.com/AlexMercer-MA/UnrealEngine-4.27/blob/306a7e9f7fb53f14c2cb3bfd3854ad906710a17e/Engine/Source/Runtime/UMG/Private/Slate/WidgetRenderer.cpp#L288-L341).

В UHT закреплённого хоста доступны запрос, расписание, режим retention и
доступ к effect material. Отдельный вызов paint/capture с передаваемым
стилем и callback после захвата отсутствуют в этом отражённом интерфейсе.
`RegisterHook` закреплённого UE4SS работает с UFunction, а существующий
frame pump вызывается из EngineTickPre. Ни один из них не даёт точку
внутри `SRetainerWidget::OnPaint`. Переключение в соседних кадрах не
изолирует Screen, а регулировка фазы родного Retainer меняет его штатное
расписание. B закрыт в пределах проверенных отражённых API и существующего
pump. Для открытия B нужен отдельный доказанный seam между захватом и
экранным элементом. [UE4SS LuaMod.cpp](https://github.com/UE4SS-RE/RE-UE4SS/blob/83330635/UE4SS/src/Mod/LuaMod.cpp).

но не доставку события. Текущий observer читает уже committed owner
из EngineTickPre и проверяет, что Screen добавлен и показан. Он не
доказывает доступность исходных данных до первого Screen paint.
World-компонент отдельно рисует в RT из собственного component tick,
если разрешает `ShouldDrawWidget`. Поэтому установка UMG Visibility
не подтверждает ни первый видимый World-кадр, ни подходящий момент
подавления stock. Надстройка оставляет Screen видимым как контроль.

подсказок. Указать частоту capture и её разрешение по времени.

1. По последовательным кадрам отметить первый кадр с Screen и первый

3. При доступном capture frame time взять длительность отдельных

   с соседним отрезком движения. Показатель FPS на экране недостаточен.

Если холодный подход по-прежнему опаздывает и фазы подтверждают
доминирующую стоимость подготовки, следующим шагом проверить
ограниченную раннюю подготовку только подтверждённо дорогой части.

fallback. Критерий готовности решения остаётся прежним: без stock

### Следующее достаточное наблюдение

После отдельного разрешения использовать один Open на известной карте.
В read-only опыте сопоставить раннюю запись из уже проверенного
BeginPlayPost с первым committed owner, а затем повторным подходом.
В callback сохранить только примитивные идентичности пары и снимок
`CanHoldPress`, lock, device, brush/UV и корневого цвета/делегата.
Проверить, была ли пара ещё вне Screen. В существующем committed
pump сопоставить ровно ту же пару и актуальные поля в момент первой
готовности. Для проверки времени использовать запись первого Screen
кадра с общей меткой; отметка `bAddedToScreen` подтверждает membership,
а не пиксели. Если замена widget, неподдерживаемый вход или отсутствие
раннего совпадения мешают, завершить опыт на конкретной границе.
Глобальные покадровые обходы и повтор прежних недоставленных hook
для этого сравнения не нужны.

Даже совпадение снимков даст основание лишь для одного ограниченного
проверочного pre-hide. Ему потребуется доказать отсутствие stock
пикселей, заметного blank и поздней перезаписи tint. При непрерывном
контроле неподдерживаемый переход должен возвращать stock без ожидания.
Если ранний путь теряет актуальную кисть до первого show, для записи
понадобится другая доказанная граница перед paint.

### Условия будущего fallback

Независимые границы — раннее подтверждение точной пары, начало
эпизода по committed owner и подтверждение нормального World.
На подтверждённой ошибке вернуть исходный RGBA сразу. Примерно 500 мс
после committed owner остаётся гипотезой срока для незавершённой
подготовки. `SHOWN` описывает команду. Его нельзя трактовать как
доказанный первый пиксель или использовать как гарантию срабатывания
fallback при бесшумном отказе рендера.

После восстановления эпизод закрепляется stock-only до следующего
подтверждённого перехода через NONE или смену owner. Поздний World
не получает право на показ. Для восстановления нужны тот же живой
экземпляр, неизменённое записанное значение и отсутствие binding.
Lifecycle-сигналы инвалидируют право на запись. EndPlay не даёт
разрешения писать в разрушаемый объект. Без доставки game-thread
callback или после уничтожения объекта watchdog не подтверждает
восстановление. Эти условия пока описывают будущий тест, поскольку
граница безопасной первой записи не установлена.

### Read-only кандидат ранней пары

Подготовлен наблюдатель для того же сундука Open из покадрового
прогона `6bfc676`. Точное имя размещённого актора взято из
`CREATED component` предыдущего прогона. Другие акторы не
обследуются. При несовпадении карты или идентичности не искать
альтернативу по всему миру. В существующем BeginPlayPost фиксируются
GetUserWidgetObject, Widget и NewUserWidget. В существующем committed
read фиксируются первый выбор и первый видимый по native-предикатам
Screen на этом owner, не более двух эпизодов. Пока Screen не готов,
проверки ограничены этим owner и 120 вызовами чтения на эпизод.
NONE, смена цели, EndPlay и карта сбрасывают соответствующее состояние.
Между callback хранятся только примитивные идентичности и счётчики.

Собрать точный Selected-owner World `2e167227`, сверив его 13 Lua
по исходному манифесту. Последовательно применить
[first-show-observe.patch](first-show-observe.patch) и
[early-tip-observe.patch](early-tip-observe.patch) в отдельной копии
через `git apply --unidiff-zero`, затем добавить
[IIPEarlyTipHUDObserver.lua](IIPEarlyTipHUDObserver.lua).
Пакет содержит 14 Lua плюс внешний локальный конфиг. Tint и патчи
подавления в сборку не входят. Протокол закрытой установки, SHA-256
и отката сохраняется. Установка требует отдельного разрешения.

Запустить обычное сохранение, записать первый подход к тому же сундуку,
отойти до исчезновения обеих подсказок и повторить подход без смены
устройства. После выхода сохранить журнал и сверить `IIP_EARLY_TIP`:
`BEGIN` с `added=false`, `SELECTED` и `SCREEN_READY` на том же
акторе и компоненте, отдельно для каждого подхода. Сопоставить видео
порядка показа. Точную привязку PTS к абсолютным логовым часам
использовать только при наличии общей метки.

- Ранний гейт — взаимная идентичность, прежний экземпляр до Screen,
  Open без удержания, читаемый исходный RGBA и пустой binding.
  Смена экземпляра или цветового контракта требует выяснить точный
  момент. `unknown` — отсутствующее доказательство.
- Поздний гейт — фактическая кисть, device, allowed/lock при показе.
  Неизвестная или ещё неактуальная ранняя кисть не делает
  BeginPlayPost поздним. Она показывает, что будущему pre-hide надо
  отдельно доказать поддержку входа или безопасный переход на stock.
- Снимки не доказывают сохранение записанного alpha при первом paint.
  При совпадении пары и раннем цветовом контракте допустим следующий
  ограниченный опыт с tint. При расхождении завершить на конкретной
  недостающей границе. При ошибке наблюдателя завершить запись и
  откатить кандидат при закрытой игре.

Политика будущего fallback остаётся прежней: немедленный возврат
RGBA при подтверждённой ошибке, ориентировочно 500 мс от committed
owner при отсутствии готовности и stock-only до завершения
неудачного эпизода.

## Раннее подавление A и подготовка ресурсов B

Оба режима ограничены тем же размещённым сундуком из `d8a9182`.
Установленный ранний порядок и идентичность достаточны для этой
исследовательской записи, с открытой проверкой первого paint.
В `BeginPlayPost` только снимается идентичность. Существующий
EngineTick pump пытается записать tint лишь после подтверждённого NONE,
повторной проверки пары, отсутствия Screen, Open без удержания,
разблокированного листа, поддержанного устройства и пустого binding.
При уже выбранном целевом Open записи нет. Читаемый исходный RGBA
сохраняется, меняется только A. Ранняя кисть при этом не используется.

При выборе World по-прежнему требует свежий штатный текст и видимый
по native-предикатам источник. Для прямого пути дополнительно нужна
поддержанная Texture2D. Наблюдавшаяся ранняя PS4-заглушка исключена.
Один World использует прежние позицию, layout и 17 параметров.
Ни иной актор, ни unsupported-вход не получают World в этом опыте.
На обычном NONE собственный World скрывается и исходный tint не
перезаписывается, поэтому повторный подход проверяет тот же механизм.

`GameplayStatics:GetRealTimeSeconds` задаёт предварительный дедлайн
0,5 с от committed owner. Это проверка в доставленном pump, а не
прерывание синхронного World.create. Явная ошибка, неподдерживаемый
вход или потеря валидной World-команды запускают возврат сразу.
При восстановлении проверяются исходная живая пара, binding и
значение, записанное пробой. Чужое значение не перезаписывается.
После отказа проба остаётся stock-only до перезапуска процесса
как дополнительное ограничение этого кандидата. F4 запрашивает
STOP. При смене карты возврат идёт из следующего pump, если объект
ещё безопасно доступен. EndPlay инвалидирует lease без setter.
Если pump не доставлен либо экземпляр уничтожен, возврат не
гарантируется. `PREHIDE_WORLD_COMMAND` подтверждает только готовую
World-команду. Бесшумный отказ фактического рендера за ней этот
watchdog не обнаруживает.

### Разница режимов и сборка

1. В отдельной копии сверить 13 Lua точного Selected-owner World
   `2e167227` по замороженному манифесту. Применить
   [first-show-observe.patch](first-show-observe.patch), затем
   [prehide-open.patch](prehide-open.patch) через
   `git apply --unidiff-zero`. Добавить
   [IIPPrehideOpen.lua](IIPPrehideOpen.lua). Это A, 14 Lua
   плюс внешний локальный конфиг. Предыдущий диагностический
   early-tip-observe и старый ручной tint в сборку не входят.
2. Для отдельного B поверх A применить только
   [prehide-early-assets.patch](prehide-early-assets.patch).
   После успешного раннего tint режим B один раз выполняет
   World.prepare и refresh_assets до выбранного Open.
   Это проверка локальных входов, разрешение host-класса и
   материала и штатная загрузка при необходимости. Повторная
   проверка доступности при создании сохранена.
3. Перед отдельно разрешённой установкой сверить SHA кандидата,
   build/UE4SS, доступность F4, внешний конфиг и ресурсы.
   Сохранить прежний активный payload и маркер вне загрузчика,
   записать SHA-256 всех файлов, переключить один маркер IIP
   при закрытой игре и проверить остальную установку. После
   выхода архивировать лог и восстановить исходный payload
   с подтверждением хэшей.

B выносит из подхода участок, ранее занявший 8,50–9,27 мс
в логовых замерах, плюс начальную проверку входов. Это ожидаемый
перенос работы, без гарантии экономии видимых миллисекунд.
Основные 39,67–43,74 мс private UI остаются. Предварительное
создание собственного компонента и дерева пока не выполнено.
Текущий World.create использует уже выбранную живую пару,
camera/anchor, локализованный текст и первичную кисть. Ранний
вызов нарушил бы существующие проверки. Отдельная безопасная
граница статического дерева и native attachment ещё не доказана.
GPU RT не прогревается, постоянный скрытый рендер не добавлен.

### Игровая проверка

Сначала A. Записать холодный и повторный подход к тому же Open
на том же устройстве. В логе `PREHIDE_PREHIDDEN` должен быть

Screen → полный World. При скрытом Screen эти интервалы
напрямую недоступны. Использовать общую визуальную границу
подхода или синхрометку, если она доступна. Не вычитать PTS
из логовых часов и не приравнивать SHOWN к первому пикселю.
Для микрофризов нужны отдельные времена кадров.

### Первый прогон A и исправление старта

Установленный A `7f497fc` подтвердился по 15 файлам. В UE4SS 654–726
есть загрузка мода, два перехода к owner и STOP по F4 с подтверждённой
отменой цикла. Записей PREHIDDEN, WORLD_COMMAND и RESTORED нет.
Пользователь сообщил, что World не появилась. Исходный прогон не
проверил сохранение раннего tint и первый paint. SHA-256 локального
журнала `a819d42f891a690b606b0b5446acc0b94f143646694abc93a2dd7a075b7d1774`.

Исходники объясняют такой исход: LoadMapPre ставит invalidate,
а следующий pump прежнего A вызывает restore и блокирует попытку даже
без lease. Офлайн воспроизведена последовательность MapPre, новый
BeginPlay и первый pump. В преемнике MapPre сбрасывает старую очередь,
а обработка invalidate вызывает restore только при активном lease.
BeginPlay новой карты сохраняет свою очередь до следующего прохода.
Добавлены метки EARLY_PAIR и EARLY_PAIR_UNAVAILABLE. Восстановление
при активном lease, STOP и блокировка после отказа сохранены.
Проверка startup-исправления в игре ещё предстоит. Режим B не испытывался.

### Повторный прогон A и уточнение причины отказа

Source `af12878`, 15 файлов сверены. Журнал 685–687 подтвердил раннюю
пару и запись alpha. Через 48,94 с, при первом выборе, строки 724–725
показали `RESTORED native_contract_lost` до создания World. Второй
подход остался stock-only. F4 отменил цикл. Обобщённая причина не
позволяет отличить возврат исходного RGBA от изменения action, hold,
lock или input. Событие RESTORED допускало как setter, так и уже
восстановленное штатное значение.

Преемник разделяет причины и пишет текущий RGBA при его изменении,
а также различает уже исходный цвет и проверенный setter. Критерии
допуска, обработка fallback и native writes сохранены. Следующий
прогон нужен для конкретного поля, а не для приёмки первого paint.
Локальный журнал SHA-256
`3c8f3b3ae3ccc36760a47bf30dde7aa78826d330b4ec2f0c5cd4bb4ff6c0ca75`.

## Источник потери раннего alpha — статический дискриминатор

Анализ после игрового `f93867e` и отчёта `d704a6d`.
Факт игры: ранний `SetColorAndOpacity(A=0)` прошёл readback.
Спустя 29,83 с в первом committed selection тот же
actor/component/TipHUD имел исходный `RGBA=(1,1,1,1)`; собственный
setter восстановления ещё не был вызван. Точный момент изменения
и инициатор остаются **UNKNOWN**.

Проверен source `UUserWidget.cpp` в закреплённом зеркале UE4.27
`306a7e9`:

- `UUserWidget::SetColorAndOpacity`, строки 296–305: присваивает
  `ColorAndOpacity=InColorAndOpacity`; при живом `MyGCWidget`
  обновляет `SObjectWidget`. Это соответствует успешному раннему
  readback, но не объясняет его последующий сброс.
- `UUserWidget::SynchronizeProperties`, строки 278–294: вызывает
  родительскую синхронизацию, берёт binding для **текущего**
  `ColorAndOpacity`, передаёт его в Slate. В теле этого метода
  нет операции восстановления значения UObject по умолчанию.
- `OnWidgetRebuilt`, строки 750–764, вызывает `NativePreConstruct`
  и `NativeConstruct`; `NativeConstruct` вызывает Blueprint
  `Construct`, строки 1331–1339. Эту границу стоит проверять,
  но сам факт вызова не доказывает, что конкретный Blueprint
  переписывает root tint.
- `WidgetComponent.cpp`, строки 1192–1224 и 57–71: при первом
  попадании в Screen передаёт `UserWidget->TakeWidget()`
  в `FWorldWidgetScreenLayer`. Такая поздняя фаза жизненного
  цикла существует, но корреляция по одному выбору не
  доказывает, что она сбросила исходное UObject-свойство.

[UE4.27 UserWidget.cpp](https://github.com/AlexMercer-MA/UnrealEngine-4.27/blob/306a7e9f7fb53f14c2cb3bfd3854ad906710a17e/Engine/Source/Runtime/UMG/Private/UserWidget.cpp#L278-L305)

**Следующий достаточный шаг — узкий локальный static writer trace.**

проверить узлы корневого `TipHUD_C` `PreConstruct`, `Construct`,

## Эксперимент Translation — исходный кандидат

Следующая UX-гипотеза после `f93867e`: root `ColorAndOpacity`
вернулся к единице до выбора, поэтому исследуем **другой**
визуальный параметр без перезаписи alpha. `CanvasPanel_0` является
сериализованным `TipHUD.WidgetTree.RootWidget` и охватывает
`HorizontalBox_4 → CanvasPanel_6`, локализованный
`TextBlock_89`, разрешённый `RetainerBox_0` и запрещённую
ветку `CanvasPanel_2` ([прежняя проверка](../../VISUAL_READINESS.md#1-actual-serialized-tree-and-slots)).

UE4.27 `UWidget::SetRenderTranslation` изменяет
`RenderTransform.Translation` и вызывает
`UpdateRenderTransform`, передающий значение в cached `SWidget`.
Метод имеет `UFUNCTION(BlueprintCallable)`; поданный им
`FVector2D` не меняет native Screen `ExtendedWidgetComponent`,
`CanShow`, UWidget `Visibility`, `RenderOpacity`,
`ColorAndOpacity`, state локализации/ремаппинга или selection.
Это **C++ source-level свойство**, не Asterigos runtime PASS.
[UE4.27 Widget.cpp](https://github.com/AlexMercer-MA/UnrealEngine-4.27/blob/306a7e9f7fb53f14c2cb3bfd3854ad906710a17e/Engine/Source/Runtime/UMG/Private/Components/Widget.cpp#L180-L229),
[Widget.h](https://github.com/AlexMercer-MA/UnrealEngine-4.27/blob/306a7e9f7fb53f14c2cb3bfd3854ad906710a17e/Engine/Source/Runtime/UMG/Public/Components/Widget.h#L459-L487).

**Состав кандидата:** `IIPPrehideTranslation.lua` (отдельный от
alpha-модуля) и `prehide-translation.patch`. Только размещённый
`0-1_lootbox_01_mat_ST001`, обычный Open без удержания на известной
сборке. `BeginPlayPost` ставит в очередь точную пару. В существующем
EngineTick pump при `READY NONE`, `bVisible=false`,
`bAddedToScreen=false`, надёжных связях actor/component/widget/root,
поддержанном action/устройстве записывается одна трансляция
`{X=original.X+16384,Y=original.Y}`. Исходная трансляция и
примитивная identity панели сохранены. Никакого глобального
поиска или регулярного setter. Число 16384 — ограниченная
исследовательская величина для 2560×1440, не рабочий механизм
любого DPI или ultrawide.

В selected-owner pump проверяется сохранность именно этой
внутренней трансформации. World может включиться только при
сохранённом lease, готовой native локализации и поддержанной
`ImageInteractAllowed.Brush.ResourceObject` типа Texture2D
без ранней дизайнерской заглушки. Исторические `Visibility`/
`RenderOpacity` проверки сохраняются. При ошибке/изменении
трансляции/дедлайне около 500 мс — отказ в stock-only,
условный возврат **только собственной** трансляции при точном
совпадении. При чужом состоянии ничего не перезаписывать.
После успешного NONE оставлять смещение для следующего
подхода; по F4 вернуть оригинал до cleanup, если экземпляр жив.
На EndPlay уничтожаемого owner запись не пытаться.

Встроенный `RenderTransform` может переписываться собственным
Blueprint/native writer — **UNKNOWN**. Также **UNKNOWN**:
влияние offscreen Slate clipping/culling на видимую поверхность,
Tick, обновление `RetainerBox`, источник актуального текста,
первый World pixel, сохранность выбранного якоря и отсутствие
настоящих Screen-пикселей. Само `bAddedToScreen=true` не
требует сохранять хотя бы один видимый пиксель. Не сдвигать
`ExtendedWidgetComponent` или весь viewport слой и не
создавать искусственный видимый пиксель.
